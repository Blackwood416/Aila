## 0. Conclusion summary

1. **Measured absolute gaps are dominated by the two prefill segments, not by the kernels we can probe today.**
   GDN prefill 4.07 s/block (36 layers) and full-attention prefill 2.85 s/block (12 layers) are 113.1 ms and
   237.5 ms per layer (charter sec 1.1). No existing bench arm times either prefill kernel, so both are escalated
   with "needs a new timing arm" (out of scope this round). Full attention is 19.8x-115.7x above its compute floors
   `[estimate]`; GDN prefill runs *inside* a 2-read+1-write global-state stream model (0.85x-1.13x of that model,
   i.e. the model itself is the problem - state lives in global memory) `[estimate]`.
2. **The two kernels that can be measured with existing tools are (i) decode MoE grouped GEMV and (ii) decode
   attention / QSA route.** Decode MoE has *zero* kernel-level measurements in the repo (floor: 25.34 MB per
   layer/token = 4.18 ms/token at 291.11 GB/s over 48 layers `[estimate]`); decode attention at len 14336 was
   measured at 1.5833 ms for 2 rows bf16 (`docs/plans/qwen38-int8kv-vec-2026-10-12.md:23`), which is 7.85x above
   the minimum-byte DRAM floor per row `[estimate]` and is explained by the 12 q-heads/KV-head K/V re-read
   amplification (not covered by the charter sec 2 negative list).
3. **MoE prefill quad gu/dn is close to its own streaming bound and its lever family is closed by charter sec 2.**
   gate/up at 160 quads: measured 1.3809 ms vs 0.929 ms no-reuse contiguous-DRAM bound (1.49x) and vs the P4
   `_nounpack` ALU oracle 0.6136 ms (2.25x, single-variable, bit-state-preserving). The 2.25x is real but the
   remaining mechanisms (SLM dequant reuse -11%, half-unpack, byte-pair LUT, qmap-private, uint64 loads, blocked
   layout) are all already disproved. Do not reopen this line.
4. **Ranking (distance from an attainable upper bound):** GDN prefill > full-attention prefill/QSA >
   decode attention (len >= 2052; head_dim 256, indexer dim 128) > decode MoE grouped GEMV > prefill quad MoE.
   Only the bottom two have ready-made bench arms; probes are written for those.
5. **Two probe requests (existing tools only, no code change):**
   K1 `--decode-gu-bench` (decode MoE wall attainment, A/A noise floor), K2 `--qsa-probe` + `--qsa-batches`
   (QSA route split at len >= 2052 gate; includes the dense controls 2048/2051). Details in 3/4.

## 2. Gap attribution (evidence strength labelled)

### 2.1 MoE prefill quad gu/dn - gap is the unpack dependency chain; lever family closed (STRONG evidence)

- Single-variable arms on the same binary and shape: `_nounpack` (all packed loads/nibble/LUT/mul dead) 0.6136 ms,
  `_nolut` (keeps packed load + nibble extraction, drops LUT gather) 0.9244 ms, original 1.3809 ms at 160 quads
  (P4 sec 2, A/B/B/A interleaved, 20 launches per sample). Interpretation: LUT gather ~0.46 ms, packed-load+nibble
  chain ~0.46 ms, FMA/issue floor 0.61 ms. None of these components is removable by a scheme that keeps the math
  (P4 sec 3). The 1.49x vs no-reuse DRAM bound and 2.25x vs the ALU oracle are therefore *structural*, not a
  bandwidth-tuning miss.
- E2E relevance is bounded by supply anyway: the 12.58 s/block expert segment is host fill 7.28 s + bank_wait
  3.76 s + compute/rest (charter sec 1.1), and H2D 46-48 GiB per block at 9.2 GB/s ~ 5.1 s does not overlap
  memory-bound compute (charter sec 1.1, 2). Kernel micro-optimization cannot move that segment without fixing supply.
- Verdict: close the kernel line. Remaining notes only: (i) the bench passes `reuse=false` while production sets
  `AILA_Q4E_4TOKEN_REUSE=true` (status sec 2.1), so the quads-in-flight weight reuse question is owned by P/D, not K;
  (ii) wgshare share 0/2/4/8 is already measured neutral within +/-1.6% at both bench shapes (prefill-bench.log).

### 2.2 Decode attention (`attention_decode`, D=256) - K/V re-read amplification (MEDIUM-STRONG)

- Measured 0.792 ms/row at len 14336 (2-row bf16 arm, 1.5833 ms). Minimum bytes: K+V per row =
  2 kv heads x 14336 x 256 x 2 B x 2 = 29.36 MB -> 0.101 ms at 291.11 GB/s. Gap 7.85x.
- Mechanism: 24 q heads / 2 kv heads = 12 q-heads per KV head; the kernel groups by query head
  (`src/ops/AttentionOps.cpp` decode path; the 09-30 audit states the same near its line 267: grouping by query head).
  If K/V were re-read per q head (no L2 credit) traffic is 352.3 MB/row -> 1.210 ms at 291.11 GB/s, i.e. above
  the measured 0.792 ms; at L2 reuse (854.6 GB/s) it is 0.412 ms, i.e. 1.92x below measured. So the measured
  point is consistent with *partial* L2 absorption of 12x read amplification; the lever is explicit GQA K/V
  sharing across q heads (the 09-30 audit lists it as unimplemented, item 3, including the caveat that caches
  already absorb part of it). Not in the charter sec 2 negative list.
- Partial-merge already exists above 1024 tokens (`docs/plans/qwen3.8-flash-next-qsa-gap-audit-2026-09-30.md`
  notes the 1024-token switch), so split-KV parallelism is not the missing piece.

### 2.3 Decode MoE grouped GEMV - floor known, attainment unknown (arithmetic STRONG, measurement ABSENT)

- Per layer/token the 10 experts are a hard byte stream: 10 x 2,534,400 B = 25.34 MB (24.17 MiB, matching
  charter sec 3.4's 24.2 MiB). Over 48 layers: 1.216 GB/token -> 4.18 ms/token at 291.11 GB/s `[estimate]`.
  Since decode is ~64 ms/token (charter sec 3.2), the kernel can only be a major term if it runs at a small
  fraction of DRAM bandwidth, or if misses (staging/H2D, CPU experts) dominate. Both are D/R questions; the
  kernel-side fork is decided by one measurement (probe K1).
- The bench arm exists (`tests/ops/Qwen4ExpKernelTests.cpp:4604` `test_decode_gate_up_bench`, experts=10,
  200 iters x 3 rounds median printed) but no historical log exists in `tmp/` (searched: no
  `decode-gu-bench` output anywhere). `AILA_Q4E_DECODE_XSPLIT` is printed by the arm but has **no reader in
  `src/`** (only `tests/ops/Qwen4ExpKernelTests.cpp:4658`), so an A/B on that flag would be a no-op; do not
  propose it.

### 2.4 Full-attention prefill / QSA - unexplained 20x-116x; per-stage evidence WEAK

- Measured 237.5 ms/layer; compute floors 2.05 ms/layer (XMX validated peak) and ~12.0 ms/layer (vector FP32
  `[estimate]`). Even at 5% XMX efficiency the floor is 41 ms/layer, so the gap is not explained by
  "not using XMX".
- The route after the gate (dense <= 2051, sparse >= 2052; `src/models/Qwen4ExpBnb4Backend.cpp:2931-2933`
  comment and `AttentionOps.cpp:4648` D256 guard) is query-tiled: score compressed indexer K per tile,
  top-512 blocks, then `attention_prefill_qsa_batched` per tile (default `AILA_QSA_BATCHED_PREFILL=true`,
  `src/models/Qwen4ExpPrefill.cpp:366-416`). Tile size is 16-64 rows (`AILA_QSA_QUERY_TILE`, budget-derived,
  `Qwen4ExpBnb4Backend.cpp:1030-1036`).
- Only per-row proxies are measured: indexer scoring 82.2-85.4 us and pre-radix TopK 385.1-589.4 us at
  len 4096-8192 per single query row (09-30 curve). Multiplying the per-row scorer by 4096 rows would exceed
  the whole segment, so the production batched scorer must be much cheaper - but this is unverified:
  there is **no timing arm for the qsa prefill path** (`--qsa-prefill-only` is correctness only).
- Independent lever (not in charter sec 2): K/V sharing across q heads and across query tiles inside the prefill
  attention, plus indexer scoring/topk fusion. Both need code + a new timing arm: escalate, do not probe this
  round.

### 2.5 GDN prefill - kernel is inside an already-degraded stream model (source STRONG, model [estimate])

- Source facts (all STRONG): one WG per value head; serial token loop; state read twice and written once per
  token from global USM with 512 B-stride column access; 5 WG barriers and 3 group reductions per token;
  `mlp_block=8` register blocking (`src/ops/GatedDeltaNetOps.cpp:440-760`).
- Model [estimate]: 2R+1W of 64 KB/token/head x 48 heads x 4096 tokens = 38.7 GB/layer -> 132.8 ms at
  291.11 GB/s; measured 113.1 ms/layer = 0.85x of the model (1.13x of a 1.5R+1W variant). The state working set
  is only 3.0 MiB/layer, so part of the traffic is L2-served; the model's DRAM assumption is the weak point,
  but both variants put the kernel within ~1.1-1.6x of a global-stream regime.
- Lever: keep the state on-chip (SLM, 64 KB/WG fits) or use the chunkwise form. Headroom to the SLM-traffic
  bound is ~12x `[estimate]`, but it is a structural kernel rewrite; the existing opt-in `GDN_CHUNK_MODE=1`
  measured only -2.7% ttft e2e (charter sec 2; status sec 3.2) with a decode regression. Escalate with a new timing
  arm request; not a bench-only probe.

### Probe K1 - decode MoE grouped GEMV wall attainment (gate/up first)

Purpose: decide whether the 25.34 MB/layer decode expert stream is kernel-limited or supply-limited.

- Shape (fixed by the arm): experts=10, in=2560, intermediate=640, blocksize=64, 200 iters x 3 rounds median,
  printed as `[decode-gu-bench] ... median_ms=`.
- Bounds: gate/up 16,896,000 B -> 58.0 us @291.11 GB/s, 30.2 us @560 GB/s.
- Decision rule (single shape - the arm has no shape knob, so the >=3% two-shape rule cannot be applied to
  K1; it applies to any future code variant):
  - `median_ms <= 0.0726` (<= 1.25x of 291.11 GB/s bound): kernel is at the DRAM wall; close the kernel line and
    send decode cost-model work to supply (staging/CPU/router).
  - `0.0726 < median_ms < 0.0871`: gray zone; repeat once (A/A) before concluding.
  - `median_ms >= 0.0871` (>= 1.5x): kernel headroom exists; draft a variant (e.g. 2 experts per WG row-group
    reuse, the decode analogue of the quad row-grouping) and gate it at >=3% at two shapes + bit-identical
    output before defaulting.
- A/A noise floor: run the arm twice in two separate processes; report both medians and the spread. This is a
  diagnostic probe: no code change, no default flip.

### Probe K2 - QSA route split at and above the 2052 gate (decode side)

Purpose: (i) separate indexer score / TopK / selected-attention costs at the gate-crossing and at 4096/8192,
(ii) decide whether the QSA route is net-positive at all on the current pair, and (iii) provide the >=3%
two-shape gate reference for any future selector/attention variant.

- Gate safety: dense control at len 2048/2051, sparse from 2052 (`Qwen4ExpBnb4Backend.cpp:2931-2933`).
  Do not shorten below 2052 for sparse-path numbers.
- Tool: `--qsa-probe` prints `[QSA COST]` JSON per stage (score/select/dense_attention/selected_attention/
  routed_post_projection) with median/p10/p90 over 20 samples x 3 rounds at lengths
  {512, 2048, 2051, 2052, 2056, 2146, 4096, 8192, 32768}. `--qsa-batches` prints `[QSA BATCH COST]` for the
  batched selector at start in {2044, 2052, 2143, 4095, 8191, 32767, 65535, 131008, 131071} x rows {4, 64}.
- Decision rule (two shapes: 4096 and 8192, both >= gate):
  - Route net-positive iff `routed_post_projection < dense_attention` at both lengths by >= 3% each (kernel-level
    default line); the pre-radix measurement was net-negative (581.1 vs 370.6 us at 4096; 812.3 vs 558.1 us at
    8192), so this verifies the radix+vec4 selector default actually fixed the route.
  - If net-positive: the residual decode-attention lever is the K/V cross-head amplification (probe K1-side
    measurement is not needed; next step is a code variant with the same >=3% two-shape gate).
  - If still net-negative at 8192: the lever is the selector/scoring, not the attention kernel; the prefill
    QSA gap (sec 2.4) is then coupled to the same code.
