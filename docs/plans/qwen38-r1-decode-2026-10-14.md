## 0. Conclusions (5 lines)

1. Median decode wall on the 14K agent shape is 64.40 ms/token; the host-observed
   budget is 60.41 ms of it (93.8%): 12.59 ms blocked on the per-layer router
   sync, 10.22 ms blocked on the CPU-expert join, 37.60 ms of actual host work
   (submits, classification, copies); sampling adds 3.45 ms outside that budget.
2. `router_wait_ms` (12.59, 19.5%) is not router compute: it is the in-order
   queue residual at 48 per-layer top-k sync points (`router_wait` =
   `actual_route_event.wait_and_throw()`, Backend.cpp:2147-2169, 2301).
3. The largest single item is `experts_host_ms` 21.04 (32.7%); inside it the
   CPU-expert join block is 10.22 (15.9%) and the rest (10.82) is hit/miss
   classification, CPU batch build, kernel submits and result copies.
4. CPU expert compute (13.88 ms for 259 misses/token) already runs at about
   45 GB/s of DRAM read; moving those misses to GPU staging is a losing
   direction (626 MiB/token at 9.2-9.8 GB/s PCIe = ~66 ms).
5. Best two probes by bound x feasibility: (C1) decode CPU/GPU share rebalance
   around the join window, bound -15.9%; (C2) decode-side PLE lookahead, bound
   -9.4%. MTP-per-session is deferred: its only legal shape measured +2.9%.

## 3. Candidate ranking and minimal probe specs

### C1 (rank 1) decode CPU/GPU share rebalance around the join window

- Bound: -10.22 ms/token (-15.9%) if the join exposure were fully hidden;
  adoption gate is the standing +5% end-to-end threshold (charter section 5.3).
- Mechanism: 259 misses/token go to the CPU; CPU service/layer is ~0.35 ms while
  the host work available between `StartArenaCold` and `JoinResidentCold` is
  ~0.10-0.15 ms, so ~0.21 ms/layer stays exposed. Options: cap CPU credits per
  layer (`AILA_Q4E_CPU_MAX_EXPERTS`), let the idle PCIe/staging path absorb a
  slice, or raise the resident hit rate.
- Engineering: S for the probe (env only), M for adoption (per-layer split
  policy plus bitwise re-verification of mixed CPU/GPU rows).
- Risk: mixing engines changes the arithmetic path for the moved rows; PCIe/DMA
  is idle in this profile but was never quantified for a per-layer slice, so the
  `=0` arm is the explicit counter-example that must be measured before any
  policy is chosen.
- Generalizability: valid for top_k <= 16 with per-layer miss <= staging slots
  (16); test shape must stay the production 14K agent corpus (well above the
  QSA/GDN decode thresholds). Do not use a sub-128-token prompt.
- Minimal probe: `dec-cpu4-b1`/`b2` with `AILA_Q4E_CPU_MAX_EXPERTS=4`, ordered
  A/B/B/A against the R1 diag arms. Fields: `cpu_join_ms`, `experts_host_ms`,
  `fill_ms`, `bank_wait_ms`, `h2d_mb`, `misses`/`cpu_tasks`, `total_ms`.
  Threshold: median `total_ms` -5% or better with 4/4 pairs won; otherwise
  no-go and the join exposure is a structural floor for this profile.

### C2 (rank 2) decode-side PLE lookahead

- Bound: -6.08 ms/token (-9.4%) if the PLE host interval were hidden behind the
  previous token's GPU tail; p10 = 0.238 ms shows the interval is already near
  zero on ~1/3 of tokens, so the realistic gain is the high mode (6.7-9.7 ms).
- Mechanism: the sampled token is known before the next `Forward`; the existing
  double-buffered ticket path already supports preparing the following block
  with `ple_next_ticket_` (Backend.cpp:1807-1826) but it is only wired for
  prefill chunks (`prefill_remaining >= 0`). Decode could pass the next token
  and reuse the same machinery.
- Engineering: S-M (ForwardOptions/Request plumbing plus ticket validation).
- Risk: ticket invalidation on cancel/truncate (existing `MatchesInput` and
  reset paths), and MTP windows would need the verified token; the PLE table
  gather also faults file-backed pages, so part of the 6.08 ms may not be
  hideable - R3 decides this.
- Generalizability: decode only (prefill already has lookahead); test at 14K and
  confirm at a >= 128-token prompt so the attention path stays above its
  fused-JM threshold.
- Minimal probe: `AILA_Q4E_PLE_ASYNC=0` vs `=1` decomposition arm (R3). If
  synchronous prepare shows the same `ple_host_ms`, the cost is gather/page
  fault work and C2 is capped; if the async arm is the expensive one, C2 applies
  by construction. Threshold: `ple_host_ms` median >= 3 ms hideable.

### Deferred (rank 3) MTP per-session gate

- Measured at its only legal shape (context 2048): +2.9% first answer (15.41 vs
  14.98 tok/s), -0.3% continuation (15.10 vs 15.15), acceptance 74.5-74.8%
  (charter:43; `docs/plans/qwen38-mtp-acceptance-2026-10-11.md`:11-16,30;
  receipts `tmp/q4e-mtp-alignment-20261011/mtp-{A2,B2}`).
- Model-level bound if the 2-row verify cost equaled one B1 step: +74.8% rate;
  the measured step cost is 1.70x, i.e. the lever is verify-kernel cost (role K),
  not the gate.
- Why deferred: the gate is `Model.cpp:772-774` (context <= 2048 at load), and
  production agent sessions start at 14K tokens, so a per-session gate would
  only ever fire during a session's first ~2048 tokens - near-zero value for
  the production workload, and below the +5% gate in the measured regime.
- Minimal probe if the coordinator still wants it: server at `--context 2048`
  with `AILA_Q4E_SERVER_MTP=1` vs `0`, prompt ~1500 + generate 128, read
  `[Q4E Server MTP] windows/accepted` plus after-first-content rate and ttft.
