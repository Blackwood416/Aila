# R1/E1 - prefill to 400+ tok/s: 4096-block six-bucket split and three paths

Date: 2026-10-15. Role: E1 (prefill 400+ tok/s target, 14K TTFT 69 -> <=35 s).
Repo HEAD `3ef4606` (pair `retained27`). Zero GPU actions in this report; every
number carries a source. Predictions are tagged `[estimate]`.

Revision 2 (same day): B5's GDN SLM variant was measured NO-GO by the
coordinator (section 2, P2). All path arithmetic and the additivity claims were
recomputed; the honest landing point of the current plan is ~365-370 tok/s,
not 436. See section 2.5.

## 1. Six-bucket split of one steady-state 4096 block (19.5 s)

Production anchors (retained20-27, 14K request, 3 x 4096 + tail):

| bucket | value | source / derivation |
|---|---:|---|
| host fill (mmap rows -> pinned bank) | 2.4 s | production arm fill_ms (parallel fill); serial arm 7.2-7.3 s, see conservation below |
| H2D copy (46.8 GiB @ 9.4 GB/s) | 5.3 s | 19,360 staged x 2.417 MiB = 46,792.97 MB (`c1-d0-worker.log` h2d_mb field); rate 9.45 GB/s measured on 618 MiB contiguous USM copy (`tmp/q4e-sprint-r1-20261014/supply-bench-2026-10-15.log` mode 4: 65.4 ms) |
| bank dependency wait | 8.1 s | production arm bank_wait_ms; contains the 5.3 s copy + ~2.8 s reader lag (copy queue in-order fence on the bank's last consumer) |
| expert kernels (device) | 0.4 s | 50.26 GB weight reads @ 116.5 GB/s effective (supply bench mode 0: 5.31 ms / 618 MiB resident); cold acts 593/layer x 48 |
| GDN kernels (device) | 4.1 s | `r1-stages2-worker.log` serialized stage arms: 4,126.9 / 4,120.9 / 4,040.4 ms |
| full attention + hc/router/head (device) | 2.5-2.9 s | same arm: 2,504.8 / 2,372.4 / 2,935.0 ms; hc 0.29-0.48 s, router 0.23-0.29 s |
| remaining host (submits, route, tail) | ~1.3 s | 19.5 minus the items above; router_wait production 7.7-8.4 s is the device queue residual inside this band |

Host-interval identity (non-overlapping, production arm):

```
19.5 s = fill 2.4 + bank_wait 8.1 + router_wait 7.7 + other host 1.3
bank_wait 8.1  ~= H2D 5.3 + reader lag 2.8
router_wait 7.7 ~= device 7.3 (GDN 4.1 + full 2.5 + experts 0.4 + router/hc 0.3)
```

**Which two items are >70%: `bank_wait` (8.1 s, 42%) + `router_wait` (7.7 s,
39%) = 81%.** Neither is kernel time: the copy stream (5.3 s) and the GDN +
full-attention device stream (6.6 s) are the two real resource owners. The
expert kernels are only ~2% of the block. Fill/bank conservation is measured:
serial fill 7.2+3.8, parallel fill 2.4+8.1, direct copy 0+0 (bank wait moves,
total ~11.0-11.8 s conserved; `qwen38-strata-c1-prefill-staging-screen-2026-10-13.md`).

Overlap of transfer and streaming compute is foreclosed on this stack by
charter section 2 (C1 transfer/compute add; C2 hardware check: copy-only
ordinal-1 H2D = 9.81 GB/s vs default 9.76 GB/s). The supply bench agrees from
the other side: mode 1/4 (background copy) stretches 5.3 ms kernels to
31.9-67.6 ms while the copy keeps 9.4 GB/s, i.e. host wall ~copy, device
timeline additive.

## 2. Three paths with arithmetic

Baseline: 19.5 s/block = 210 tok/s. Target: <=10.2 s/block = 400+ tok/s
(and <=9.9 s/block for the 35 s 14K TTFT).

### P1. Bytes: per-prompt cold-key union (-7.1 s of resource, -7.35 s of wall)

Measured: per layer and prompt the cold union is 454-512 keys while each chunk
re-stages 403 cold keys (76,060 staged over the 14K prompt vs a 21,792-key
union floor; P-1 export: 24,352/24,576 keys touched, `qwen38-r1-prefill-supply-2026-10-14.md`
section 3.2). Promotion of used cold keys into resident slots (the existing
`ExecuteSwapsAsync`/gain machinery, driven from the prefill route instead of
the decode hotset) cuts staged keys per chunk from 403 to ~128/layer.

```
copy 5.3 -> 1.6 s, fill 2.4 -> 0.7 s, reader lag 2.8 -> 0.85 s  (lag scales with bytes)
wall 19.5 -> 7.7 (device) + 2.45 (bank_wait) + 0.7 (fill) + 1.3 (other) = 12.15 s = 337 tok/s
```

Engineering: M-L (prefill-side promotion policy; the layer-major v1-v4 code is
evidence that the *restructured* loop regresses, so this must keep the
chunk-major loop verbatim). Risk: resident slots are the decode hotset's
lifeblood (2,792 slots shared); promotion must be per-prompt and revert after
the prefill. Minimal verification: 8192-pair A/A with the promotion arm; gate
H2D >= -40% and wall >= +5%.

### P2. GDN: SLM variant measured NO-GO; only the no-SLM rewrite qualifies

Coordinator A1 run of `AilaQwen4ExpGdnBench.exe` (4096 rows: baseline 74.59 ms;
slm_r0 71.14; slm_r56 120.09; slm_r120 138.68; 8192 rows: 149.06 / 142.18 /
239.34 / 276.83; all bitwise-equal): keeping the state in SLM (r>0) collapses
occupancy/bank behavior (-61% to -86%). The only survivor is the no-SLM rewrite
(r=0) at -4.6% kernel, i.e. -3.45 ms/layer x 48 = **-0.17 s/block = -0.6%
TTFT, below the pre-registered gate** (K4's gate was kernel <=45.5 ms/layer;
74.59 -> 71.14 does not come close).

Consequence: the K4 "8x space" is NOT addressable by SLM residency. The
column-split route is also closed (the GDN output RMS norm reduces over all
128 columns; `src/ops/GatedDeltaNetOps.cpp:730-740`). P2 is downgraded to a
free-standing -0.17 s contribution and no longer counts as a path to 400.

### P3. Reader lag: decouple the copy queue from the bank's last consumer

Measured: bank_wait 8.1 s > copy 5.3 s. The excess is the in-order copy queue
fenced on each bank's previous consumer (`StageColdExpertsAsync`:
`cgh.depends_on(staging_reader_[pp])`), plus the 2-bank ping-pong depth (77 MiB
= 8.3 ms of lookahead). Mechanism vs charter section 2: C2 (and the
`copy-only` hardware screen) tested WHERE the copy executes - queue group and
placement; A770 exposes an ordinal-1 copy-only group but its H2D rate equals
the default queue (9.81 vs 9.76 GB/s). P3 tests WHEN the next H2D may start
relative to the bank's consumer; no path here makes the transfer faster or
moves it to another engine.

```
bank_wait 8.1 -> ~5.5 s; wall 19.5 - 2.8 = 16.7 s alone = 245 tok/s
marginal after P1: only the residual 0.85 s is left to remove
```

Engineering: S-M (bench first; then a 3rd/4th staging buffer). Cost: 16 slots x
2.417 MiB device + pinned host per extra bank (~40 MiB each).

### 2.5 Combined, with corrected additivity

P1 and P3 both act on the same bank-wait term: after P1 shrinks the byte stream,
lag shrinks proportionally, so P3's marginal gain after P1 is <= 0.85 s, not
2.8 s. Applying them in order (P1 first, then P3's residual, then P2's -0.17):

```
19.5 (baseline)
  -7.35  P1 (bytes: copy+fill+lag)
  -0.85  P3 residual (what is left of the reader lag)
  -0.17  P2 (GDN no-SLM rewrite)
= 11.13 s = 368 tok/s  [estimate]   -> 14K TTFT ~39.4 s [estimate]
```

At that point the wall is device-bound (router_wait 7.7 s of the 11.1 s), so
crossing 400 tok/s (10.2 s) and the 35 s TTFT (~9.9 s/block) needs one more
device-side cut of ~1.0-1.2 s. Candidates, none of them probe-verified today:

1. full attention 2.5 s/block: 115x above the XMX bound (K1 account), no
   mechanism selected; QSA was measured only on the routed attention path
   (K2: +37% net at length >= 8192, grey at 4096) and would need a production
   shape re-anchor.
2. GDN stage 4.1 s: kernel is 3.58 s of it (74.59 ms/layer); the two NF4
   projections + dispatch are ~0.5 s and are supply/kernel mixed.
3. The 1.3 s "other host" band (submits/route/tail) - unmeasured split.

```powershell
# 2. P1 sizing (config-only) once a promotion arm exists: 8192 pair, H2D >= -40%.
#    (no command today: the promotion policy needs the M-L implementation.)
```

Read order: `[BLOCK MEDIAN] copy` (expect copy_ms ~5,300 with `copy_gbps` ~9.4;
A/A difference <=3%), then `block` (bankwait_ms - copy_ms = the P3 upper bound;
`block` wall - `copy` wall = the device coupling), then `kernel`.

Decision rules: P3 GO only if bankwait >= copy + 1.5 s at banks 2 AND the gap
closes by >=50% at banks 4 (else NO-GO and the 0.85 s residual is unresolvable).
P1 GO per its own A/A gate (H2D >= -40%, wall >= +5%). P2 contributes -0.17 s
regardless; keep it only as part of a larger change, not as a standalone gate.

Implementation order: P3 bench (hours) -> P1 (M-L, largest bound) -> any
device-side attention candidate (needs its own K-role screen).

## 4. Difference from the charter section 2 negative list

- `chunk 8192`: not used by any path; all work stays on 4096 chunks.
- `staging 64` (depth): not used. P3 changes the *number* of ping-pong banks
  (2 -> 3/4 at 16 slots) to move the reader fence off the critical path; the
  roadmap negative (-0.7%, resident-slot theft) tested depth at 2 banks, which
  keeps the fence binding.
- `strata C1 (stream-ahead)` / `C2 (copy-only queue)`: neither is re-run. P3
  does not make the transfer faster or look further ahead for the *fill*; it
  removes an in-order fence between the copy queue and the compute queue.
  C2's measured hardware result (copy-only ordinal 1 = default speed, 9.81 vs
  9.76 GB/s) is quoted as closed, not retested.
- `ring 4`, full-`pinned`, `DirectStorage`: untouched.
- SLM residency for GDN is now itself a measured negative (coordinator A1,
  section 2 P2) and is NOT proposed anywhere in this report.

## 5. Open items / non-claims

- The P3 residual (bank_wait - copy = 2.8 s) is derived from two arms measured
  under different fill regimes; the block bench measures it under one roof
  [estimate until the bench runs].
- P1's promotion policy is not designed here; the 128/layer figure assumes the
  chunk-2/3 cold sets are largely a subset of chunk 1's (P-1 union arithmetic)
  and that promotion does not evict decode hotset entries that later chunks
  need.
- Expert-kernel time uses the resident 8-rows/expert rate (116.5 GB/s); the
  production cold mix is 213 singles + 190 pairs per layer, whose effective
  rate may be lower; even 2x slower keeps the bucket under 1 s.
- The 400 tok/s target is NOT closed by the current three paths (section 2.5:
  368 tok/s bound). A device-side attention or GDN-projection channel of
  ~1.0-1.2 s is still missing.
