# MTP：8-bit KV cache 实测

2026-10-06，A770 / driver 32.0.101.8724 / oneAPI 2026.1，原 1833-token CLI system prompt、128 outputs、T2、CPU18 A64、64 draft slots，沿用上一轮保留配置。

**当前短上下文场景，现有 FP8 KV 不适合作为 decode 20+ 的突破点。** 完整 LIVE 从 BF16 的 19.7761 变为 FP8 的 17.0546 tok/s，生成与接受轨迹也改变。追加的 K 向量读取改善了 FP8 微测，但仍慢于 BF16。两项实验分支均已归档，标准 FP8 编解码修复和聚焦测试保留。

这里试的是单字节存储的 FP8 E4M3FN，Tensor dtype 使用 f8_e4m3，让已有 attention/append 分发识别格式；不是带动态 scale/zero-point 的 UINT8。没有声称这次结果覆盖所有 8-bit KV 方案或更长上下文。

## 接通范围与容量

Qwen4Exp 原先固定分配 BF16 KV；已有 attention_decode、copy_to_cache、packed QKV prepare、cached prefill 内核支持 FP8。临时 AILA_Q4E_KV_FP8 只切换 target 的 full-attention K/V，容量限制到 2048，未扩展稀疏 QSA 路径。draft KV、indexer、GDN、PLE 和权重精度不变。

本模型 48 层里只有 12 层 full attention，Hkv=2、D=256。capacity=2048 时，target full K+V **48 MiB → 24 MiB**。36 层 FP32 GDN 和 conv 状态不随之缩减；118,038,528-byte 回滚状态也不因此缩小。

本轮故意保留原 BF16 的 admission reserve 估算，target slots 始终为 3418、hot slots 3402，没有把省下的 24 MiB 换成额外专家槽。两次首尾 hotset identity 均为 7625625710176325289。

## 必要修复：原 FP8 编解码不符合标准

原实现使用了错误的指数偏置与子正规范围，并在 e>=15 时过早饱和。比如标准 1.0 的字节应为 0x38，旧实现使用 0x40；0.00390625 在旧编码中会落到零，128 会提前饱和到旧最大值 224。

保留 src/ops/Ops.hpp 的修正：bias=7，最大有限值 448，最小正规数 2^-6，子正规步长 2^-9，round-to-nearest-even，Inf 饱和、NaN 保留为 canonical NaN、有符号零保持。它修复已有 FP8 路径的转换；BF16 数学路径不变。

tests/ops/Qwen4ExpKvFp8Tests.hpp 使用独立 ldexp 标准值表，检查全部 256 个码字、相邻值中点及邻近 float、全部 65536 种 BF16 位模式的 CPU/GPU 编解码。追加/转置后的 cache 字节和未写区域 canary 也核对。数据读取后与相同 FP8 数值展开为 BF16 的既有 attention 比较，输出逐位相同、USM delta=0。

## 同值 attention 微测

形状为 B=2 个连续因果查询，Hq=24/Hkv=2/D=256，长度 1833、1834，容量 2048，fused sigmoid gate。每个采样覆盖两行提交到同步完成；3 次预热、20 个交错 wall samples，中位数。输入静态，未包含 cache 初始化/写入，不是 device profiling 时间。

| 构建 / 分支 | BF16 展开值 ms | FP8 ms | FP8 p10 / p90 ms |
|---|---:|---:|---:|
| 原读取路径 | 0.46085 | 0.79580 | 0.7800 / 0.8234 |
| 向量版 EXE，开关关闭 | 0.48245 | 0.81315 | 0.8044 / 0.8450 |
| 同一向量版 EXE，开关开启 | 0.46325 | 0.51045 | 0.5076 / 0.5259 |

向量版只改 head_dim=256 exact-merge 的 K 读取：uchar8 成组加载，用向量整数位操作解码，保持每行八项累加顺序；V 路径不变。微测输出仍逐位相同。同 EXE 的 FP8 区间缩短约 37.2%，但在相同数据上仍慢于 BF16。因此没有继续做完整模型的向量版 campaign，也没有把它推广为默认 dispatch。

日志：tmp/mtp-kv-fp8-unit.log、tmp/mtp-kv-fp8-vector-control-unit.log、tmp/mtp-kv-fp8-vector-unit.log。该形状下 K/V 已很小，压缩的 DRAM 理论收益不能替代软件解码与实际 wall time 测量；未获得硬件带宽或 cache-hit counters，不断言某个精确的缓存命中率。

## 完整生成：策略筛选，不是相同轨迹算子加速比

| 同 EXE | BF16 KV | FP8 KV |
|---|---:|---:|
| 完整 decode tok/s | **19.7760593** | 17.05457202 |
| 循环 ms | **6472.4725** | 7505.3188 |
| prompt→128 outputs ms | **17749.8829** | 18793.3961 |
| 暖完整窗口 verify ms | 78.025587 | 90.499236 |
| 暖完整窗口 advance | 1.760563 | 1.726027 |
| target CPU tasks | 24397 | 26367 |
| draft misses | 431 | 436 |

实际 EXE hash 与驱动见同名 JSON，两次 hash 相同、exit=0、LIVE USM delta=0。完整输出从 index 36 起不同，advance 也不同。因此 -13.76% 是该配置的观察结果，不能全部归因为 FP8 算子变慢；MoE 路由和验证窗口工作量也改变了。

原 BF16 T2 仍在 indices 123–127 与自己的 T1 参考不同；FP8 T2 则从 index 16 开始与自己的 FP8 T1 参考出现分歧。这与“FP8 T2 对 BF16 T2 从 index 36 不同”是两个比较。未做语言质量评估，不能从 token 差异直接给出质量下降百分比，也不能称为无损 MTP。

完整请求区间包含 target prompt、draft KV 初始化和生成，不包含模型加载、tokenization、IPC 和探针预分配；没有把 post-first 20.321 当成完整 20+。
