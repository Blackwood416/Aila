# Qwen3.8-Flash-Next：跨块提前准备 PLE

基于 `a83cd80` 的原生大页驻留版本，本轮只保留一个执行顺序优化：把下一块已知 prompt 的 PLE 准备，与当前块的模型计算重叠。两对 A/B、B/A 实际请求中，14K 长请求从约 102 秒降到 75 秒，缩短约 **26.8%**。真实 PI 工具任务分别缩短 **12.0% / 10.3%**。decode 仍约 13 tok/s，20+ 目标未达到。

硬件实查为 A770 16 GiB、驱动 32.0.101.8724、E5-2696 v3 18 核/18 线程；编译器实查为 oneAPI 2026.1.0 Build 20260617，oneDNN 3.11.2。沿用单会话、32K 容量、chunk4096、reserve3584、18 个 CPU 专家线程、BF16 KV、MTP 关闭。专家 GPU/RAM 补集、大页分配、NF4 算术、GPU kernel 和缓存交换策略没有变化。

轻量诊断只扩展原有 `AILA_Q4E_WORK_SUMMARY`，记录主机区间与原有 CPU 统计，没有插入 GPU 等待或 barrier。初始直接 14K 请求的后两个完整 4096-token 块，PLE 主机区间分别为 13.07 / 13.71 秒；同期专家 staging 填充约 7.30 秒、bank 等待约 4.4 秒。PLE 直到当前块开始才准备；其 n-gram lookup 只依赖已知输入和前两个 token，却只能与第 0 层计算重叠。这里的 PLE 区间包括数据准备/就绪等待及调用开销，不是磁盘硬件时间；第一次大块还有工作区扩容和 JIT，单独保留在原始记录。

诊断还看到普通 decode 样本每 token 约 408–421 个专家在 CPU 上运行，CPU compute 约 21–23 ms、join 约 15–18 ms，完整 Forward 约 72–74 ms。这些区间存在重叠，没有用总耗时减 CPU join 推导 GPU 成本。最初发现的 NF4 运行时整数除法和较晚的 resident dispatch 均未在本轮修改。

实现通过 Request → Session → ForwardOptions 传递一个已知的后续块，仅在调用期间借用指针。prepare 立即把 token 复制到原有双缓冲的另一槽，再由原有线程后台完成 hash、取数、解量化和 H2D。未来票据只保存数据准备状态，不推进 KV、PLE 卷积状态或 session 长度。下一次 Forward 核对 session、generation、位置、前两个 token、输入长度和实际 token 内容后使用票据；reset/truncate 使它失效。被取消的准备任务只使用模型自身持有的输入、权重和 staging，模型析构仍先等待 PLE 线程/传输，再释放这些资源。

预分配的两个 PLE staging 槽和现有线程直接复用，没有新增线程池、GPU/Host USM 缓冲或权重副本。内部接口只增加下一块输入，HTTP/IPC 接口不变。测量用的 `AILA_Q4E_PLE_LOOKAHEAD=0/1` 已从运行时代码移除；普通 Server prefill 在现有 PLE async 启用时自动使用该路径。没有新增启动参数，`tools/server/start-qwen38.ps1` 可直接使用。CLI 未传后续块的调用仍逐块执行，不宣称 CLI 获得同样收益。

固定输入来自 `tmp/q4e-agent-corpus-v1`，文件、token 和请求 hash 保存在同名 JSON 与各次原始结果中。四次运行顺序为 A1 → B1 → B2 → A2；A 为当前块开始才准备，B 为提前准备下一块。正式测量关闭 WorkSummary、stage/component profile、trace、Worker 日志捕获等诊断。每次新 Worker 就绪后的第一个业务请求均为真实 PI，随后执行取消恢复、14K 摘要和精确前缀续轮。没有把预热业务请求移到计时之外。

A1 使用改动前运行逻辑加关闭的轻量汇总代码；B1/B2/A2 使用相同 Worker 二进制，只切换实验开关，其中 B2/A2 是同二进制的反序比较。两对显示约 27% 的长请求收益后停止性能复测，没有做线程数、chunk、缓存策略或精度扫描。它是这个固定单流任务的测量，不是所有提示或完整 32K 输入的性能保证。

定向验证：`AilaRequestStateTests` 通过（0.12 秒）；`AilaQwen4ExpModuleTests --ple-only` 通过（约 9.13 秒）。后者使用真实 PLE 权重，覆盖 65→7→1 三块、EOS 历史边界、交替 staging、完整输出及卷积状态逐位一致、丢弃旧输入后重试，并核对没有新增设备分配。四次生产式请求序列均完成真实 PI、断开后 READY 恢复及长上下文续轮，正常退出，无强杀。

移除实验开关并重编后的最终验证，额外在一个新长 prefill 的首字前断开：没有内容排队，IPC 排空后新请求在 **2.04 秒**内正确返回 READY，服务正常退出 0。取消仍按 chunk 边界生效；该首次大块排空用了 **52.41 秒**，没有宣称即时取消。取消记录的 generated_tokens 为 null，表示没有最终 Worker 用量快照；首版探针错误要求必须为 0，导致断言失败，但服务仍正常退出。修正为核对 disconnect、未排队内容和实际排空，再运行恢复请求后通过。失败和成功记录分别保存在 `final-cancel/`、`final-cancel2/`，不进入性能统计。
