# E2: decode to 20+ tok/s (MTP permitted) - cost model and path selection

2026-10-15. Basis: HEAD `3ef4606`, pair `retained27`
(`build_info.json` = `681a06e`, worker exe built 2026-10-15 20:29; the
`d1-smoke` run at 20:34 is the first retained27 decode log). All numbers
below carry their evidence path; numbers marked `[est]` are estimates.
No build, no GPU arm and no commit was made by this role.

Target: decode >= 20 tok/s (currently 16.65 tok/s on the continued 14K
request; ForwardWall median 58.79 ms). 20 tok/s = 50.0 ms per emitted
token. MTP is allowed.

## 0. Executive summary

1. Post-PLE-fix T1 token wall is 58.79 ms (n=124) and splits into:
   `submitted` 55.0 + sample 3.42 + prepare/drain 0.12. Inside
   `submitted`, the two big serial terms are the per-layer host residual
   family (~9.0 ms) and the experts segment (20.65 ms, containing
   `cpu_compute` 13.25 and `cpu_join` 9.08). To reach 50 ms without MTP,
   at least two families must yield ~4-5 ms each; no single measured
   term is 8.8 ms of pure slack.
2. MTP width-2 arithmetic: rate = (1+p)/W where W is the verify-window
   wall. Measured p = 0.745-0.748 (served prompts), W = 88-106 ms
   (archived epochs), T1 = 58.8 ms. 20 tok/s at p=0.748 needs
   W <= 87.4 ms; at p=0.85 needs W <= 92.5 ms. So MTP is 0-20 ms of
   window shave away from 20 tok/s, but it has never been re-measured on
   retained27, and its correctness story (T1 divergence) is still open.
3. Recommended order: (P1) re-anchor MTP on retained27 with
   WORK_SUMMARY to get the verify-cycle decomposition, then shave W;
   (P2) T1 host-side shave (residual family + join overlap + sample) as
   the no-MTP route to 50 ms; (P3) long-context MTP enablement is a
   separate project gated on the <=2048 load-time gate and per-prompt-
   token draft Step cost (0.68 ms/token) - do not start before P1 lands.

## 2. MTP path arithmetic

### 2.1 Window structure (code)

`Qwen4ExpMtpRuntime::ForwardWindow` (`src/models/Qwen4ExpMtpRuntime.cpp:94`):

1. `draft->Step(...)` - draft proposal (`:99`), `Select(1)` greedy+D2H (`:100`)
2. `Capture(s)` - GDN/PLE checkpoint memcpy, ~118 MB (`:101`, `:68`)
3. verify: `ForwardImpl(ids, 2, decode_verification=true)` (`:113` region)
4. `Select(2)` (`:113`), accept decision (`:115`)
5. reject path: `Restore` + 48-layer 1-row GDN replay + PLE ring writeback
   + ngram recompute (`:119-135`); accept path: one more `draft->Step`
   (`:137`)
6. `ctx.synchronize()` per window (`:142`)

Enablement gates today: load-time `maxSequenceLength <= 2048` and
`GDN_CHUNK_MODE==0` and `!LM_HEAD_Q8` (`src/inference/Model.cpp:726,800`);
draft capacity `<= 2048` and `<= cfg.indexer_budget`
(`src/models/Qwen4ExpMtpDraft.cpp:149`). The 32K server therefore never
enables MTP.

### 2.3 Formula and threshold tables

Width 2 (draft 1, verify 2 rows):

```
rate = (1+p) / W            W = D + K + V + C
W = window wall (ms), D = draft steps, K = checkpoint+input,
V = verify forward, C = commit/replay
20 tok/s  <=>  W <= 50 * (1+p)          [ms]
+5% gate  <=>  W <= 1.05 * T1 * (1+p)/T1 ...  <=>  W <= 56.0 * (1+p)  at T1 = 58.8
```

Threshold table (T1 = 58.8 ms; D+K+C ~= 9.5-10.5 ms from 2.2):

| p | W_max for 20 tok/s | V_max ~= W_max - 10 | m_max = W_max/T1 | W_max for +5% gate |
|---:|---:|---:|---:|---:|
| 0.70 | 85.0 | 75.0 | 1.446 | 95.2 |
| 0.748 (measured) | 87.4 | 77.4 | 1.487 | 97.9 |
| 0.80 | 90.0 | 80.0 | 1.531 | 100.8 |
| 0.85 | 92.5 | 82.5 | 1.573 | 103.6 |
| 0.90 | 95.0 | 85.0 | 1.616 | 106.4 |

Reading: at today's acceptance the MTP window must land at <= 87.4 ms;
the archived best warm window is 87.9 ms (advance 1.848), the 10-11
server-equivalent window is ~112 ms. The single number that decides
everything is W on retained27 - it has never been measured. That is arm
M1 (section 3.1).

Width K (verified rows = K+1, independent accept assumption):

```
tokens/cycle T(K) = 1 + p + p^2 + ... + p^K
required W <= 50 * T(K)
```

| K | T(K), p=0.748 | W_max |
|---:|---:|---:|
| 1 (width 2) | 1.748 | 87.4 |
| 2 (width 3) | 2.307 | 115.4 |
| 3 (width 4) | 2.725 | 136.3 |

Width 3 buys 27.9 ms of extra budget for one more draft Step (~8 ms)
plus one more verify row. With the 09-30 conditional acceptance
(q2 ~= 0.63 from 24/38 in `qwen3.8-flash-next-p4-mtp-results-2026-09-30.md`)
T(2) = 1 + 0.748*1.63 = 2.219 -> W_max = 111.0 ms. Width 3 is a
conditional candidate: it wins iff the marginal verify row is cheaper
than T(2)/T(1) budget arithmetic allows (~14-20 ms). Needs a measured
3-row verify cost (no such measurement exists today).

### 2.4 Per-session enablement at 4K / 8K / 16K

Both W(L) and T1(L) grow with L (verify and T1 both run the same 48-layer
loop; draft attention grows O(L) too). What matters is the ratio. Gate
per session:

```
enable iff  p_hat(L) >= 1.05 * W_hat(L) / T1(L) - 1      (+5% default gate)
       and  p_hat(L) >= 20 * W_hat(L) / 1000 - 1          (20 tok/s target)
```

With T1(4K..16K) ~= 58.8-59.5 ms [est: attention share grows ~<1 ms;
basis d1-smoke full_host 2.87 at 14K], the 20 tok/s requirement stays
W <= 87-88 ms at any of these contexts - i.e. the context length barely
moves the window constraint; it moves p(L), which is unknown beyond
2048 (gate). So per-session enablement is not a workaround for a bad W:
it only decides who pays the risk when W is already <= ~88 ms and
p(L) is measurable per workload class.

Benefit curve vs W (p=0.748, T1=58.8; uplift = 1.748*58.8/W - 1; this
applies essentially unchanged at 4K-16K since T1(L) moves <1%):

| W (ms) | 87.4 | 90 | 95 | 100 | 105 | 112 (10-11 server) |
|---|---:|---:|---:|---:|---:|---:|
| rate tok/s | 20.0 | 19.4 | 18.4 | 17.5 | 16.6 | 15.6 |
| vs T1 (17.0) | +17.6% | +14.2% | +8.2% | +2.8% | -2.1% | -8.2% |

Enablement curve to measure (all under arm P3-0, section 3.3):

| L | T1(L) [est] | W needed for 20 at p=0.75 | p needed for +5% at W=95 | comment |
|---:|---:|---:|---:|---|
| 2048 | 58.8 | 87.4 | 0.696 | current legal limit |
| 4096 | ~58.9 | 87.4 | 0.696 | needs gate lift |
| 8192 | ~59.0 | 87.4 | 0.697 | needs gate lift |
| 16384 | ~59.2 | 87.4 | 0.699 | needs gate lift |
| 32768 | ~60-62 | 87.4 | 0.70-0.72 | 32K server; plus 22 s draft ingest at 0.68 ms/token |

### 2.5 Conditions for the 32K server at >= 20 tok/s

```
avg rate = (1+p(L)) / W(L) >= 20/s  with  W(L) = D + K + V(L) + C(L)
=>  V(L) <= 50 * (1+p(L)) - (D + K + C)
```

At p=0.748 and D+K+C ~= 10 ms this is V <= ~77 ms at any L. Because the
verify is a 2-row forward through the same loop, V inherits every T1
shave 1:1; the T1 host-shave path (P2) is therefore also the MTP enabler.
Two additional 32K-specific costs must be solved for enablement, not for
the 20 tok/s number itself:

1. draft ingest: 0.68 ms/prompt token -> 22.3 s on a 32K cold prompt
   (needs chunk-batched draft Step, `Qwen4ExpMtpRuntime::AfterForward`
   currently calls `draft->Step` per token, `:52-55`).
2. draft capacity: `Draft.cpp:149` requires capacity <= 2048 and
   <= indexer_budget; beyond that the draft must switch to its own QSA
   route (it already builds `indexer_k` and compress blocks every 4
  positions, `Draft.cpp:201`, but its attention is dense
   `attention_decode` over `position+1`, `Draft.cpp:208`).

## 3. Three paths to 20+ (ordered)

### 3.1 P1: re-anchor MTP on retained27, then shave the window

- Goal: W <= 87.4 ms at p=0.748 (or <= 92.5 at p=0.85); floor for the
  decision is arm M1.
- Effort: S for M1 (config only); M for shaves (see below).
- Risk: the T1-vs-MTP divergence is unresolved (deterministic, but not
  bit-equal; `bitwise_t1_guarantee=0` log line,
  `Qwen4ExpMtpRuntime.cpp:27`). Any default enablement needs a stated
  quality position first.
- Arm M1 (A/B/B/A, GPU, ~4 x 4-5 min):

```powershell
Get-Process AilaWorker,AilaServer -ErrorAction SilentlyContinue   # must be empty
python tmp/q4e-resident-speed-20261009/run_mtp_ab.py mtp-reanchor-a1
python tmp/q4e-resident-speed-20261009/run_mtp_ab.py mtp-reanchor-b1 AILA_Q4E_SERVER_MTP=1 AILA_Q4E_WORK_SUMMARY=1
python tmp/q4e-resident-speed-20261009/run_mtp_ab.py mtp-reanchor-b2 AILA_Q4E_SERVER_MTP=1 AILA_Q4E_WORK_SUMMARY=1
python tmp/q4e-resident-speed-20261009/run_mtp_ab.py mtp-reanchor-a2
```

  Read: `[Q4E Server MTP] windows/accepted` in `*-worker.log` (p_hat);
  count=2 `[Q4E AdaptiveWork]` medians in the b-arms (verify-window
  decomposition: submitted/router_wait/experts_host/cpu_compute/
  cpu_join/residual family); SSE rates in `*/result.json`. Compute
  W_hat = (1+p_hat)/rate_b. Pass = B rate >= 1.05 x A rate with the
  A/A floor of section 1.1; diagnostic = m_hat = W_hat/T1.
- If 1.49 < m_hat <= 1.7, the shave menu inside W (in order): (i) rerun
  the C2 marker buckets inside the verify window
  (`AILA_Q4E_DECODE_STAGE_EVENTS=1`, compare mechanisms not absolutes -
  observer effect was +11-13 ms, `qwen38-r1-decode-boundary-2026-10-15.md`);
  (ii) kill redundant syncs (`Select(1)`/`Select(2)` D2H + per-window
  `ctx.synchronize()`, `MtpRuntime.cpp:100,113,142`) and overlap the
  next draft Step with host bookkeeping; (iii) draft cost (two Steps,
  7.6-8.2 ms): the draft runs its own 10-expert MoE per Step - check
  slot/lockstep cost with the existing draft 64-slot cache.
- If the verify buckets mirror T1 (same 9 ms residual family + join),
  then P1 collapses into P2 and should be evaluated jointly.

### 3.2 P2: T1 host-side shave to 50.0 ms (no MTP)

- Goal: wall <= 50.0 ms (16.65 -> 20.0 tok/s), bit-equal SSE output.
- Mechanisms: (a) submit/join pipelining for the experts segment
  (cpu_join 9.08 inside experts_host 20.65); (b) residual-family shave
  (~9.0 ms of submit-side host work); (c) sample 3.42 ms fusion.
- Effort: M-L (new `src/models/Qwen4ExpDecodePlan.{hpp,cpp}`, default
  off). Do not retry the two D1 env variants or CPU_MAX_EXPERTS=4
  (closed: 3ef4606 message; `receipt-dc1-cpu4.json` -37%).
- Risk: GDN/state-order hazards if submissions are reordered; mitigation
  is same-order submissions with only join/anchor moves - the decode
  path must stay bit-exact (sampling unchanged).
- Arm P2-1 (baseline refresh is already d1-smoke; prototype arm):

```powershell
python tmp/q4e-sprint-r1-20261014/run.py p2-joinplan-a1 --prime --diag --AILA_Q4E_DECODE_PLAN=join2
python tmp/q4e-sprint-r1-20261014/run.py p2-joinplan-b1 --prime --diag
python tmp/q4e-sprint-r1-20261014/run.py p2-joinplan-b2 --prime --diag
python tmp/q4e-sprint-r1-20261014/run.py p2-joinplan-a2 --prime --diag --AILA_Q4E_DECODE_PLAN=join2
```

  Read: `tokens_s` on the 14000-continue line (`*-run.log`), ForwardWall
  medians (`*-worker.log`), residual-family fields. Pass = continued
  rate >= 20.0 and 2/2 pairs over the A/A floor; guard = content hash
  equal to the A arms (bit-exact requirement).

### 3.3 P3: long-context MTP enablement (conditional, only after P1)

- Goal: legal MTP at 4K/8K/16K sessions, then per-session enablement per
  the 2.4 gate; 32K only after draft ingest is batched.
- Required code (draft only, coordinator approval before edits):
  lift `Model.cpp:800` cap to the intended contexts; extend
  `Draft.cpp:149` capacity and give the draft a QSA-routed attention
  path beyond `indexer_budget`; batch `AfterForward` draft ingest
  (`MtpRuntime.cpp:52-55`) to chunk rows.
- Effort: L. Risk: acceptance p(L) at long contexts is completely
  unmeasured; divergence story still open.
- Arm P3-0 (after the gate lift, ctx 4096, prompt 3500, generate 128):
  measure p(4K) and W(4K) with the same protocol as M1; pass =
  p_hat(4K) >= 1.05 x W_hat/T1 - 1 for the +5% gate, and report the
